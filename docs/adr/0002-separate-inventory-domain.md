# ADR-0002: Inventory 도메인 분리

## Status
Accepted

## Context
README에 명시된 이 프로젝트의 핵심 문제는 "대용량 트래픽 및 데이터 정합성"이며, 그 실체는 대부분 좌석 하나를 여러 명이 동시에 예약 시도하는 상황에서 발생한다.

**질문**: 좌석 가용 상태(선점/잠금/해제)를 공연 메타데이터(제목, 아티스트, 가격 등)와 같은 애그리거트(`Product`)에 둘지, 별도 도메인으로 뺄지.

## Decision
별도 도메인으로 분리한다.

동시성 제어(락, TTL, Kafka Stream 반영)는 공연 정보 CRUD와 변경 빈도·일관성 요구가 완전히 다르므로 독립적으로 진화시킬 수 있어야 한다는 이유였다.

이름은 최초 `Seat`로 제안했으나, [ADR-0004](./0004-keep-generic-product-naming.md)의 멀티버티컬 확장 계획(숙소 객실, 항공 좌석 등)을 감안해 "판매 가능한 수량/상태"라는 상위 개념인 `Inventory`로 최종 채택했다. `Seat`로 두면 숙소 도메인이 붙을 때 새 도메인이 또 필요해진다.

## Consequences
- 지금은 좌석 단위로 구현하더라도, 피벗 시점에 도메인 자체는 바뀌지 않고 내부 구현만 바뀐다.
- `Booking`은 `Inventory`의 재고 확정/해제와 연동되는 트랜잭션 경계로 남는다.
