# 도메인 모델 (1차)

TicketSpring은 콘서트 티켓팅으로 시작하지만, 향후 숙소·항공 등 범용 예약 플랫폼(야놀자, NOL 유형)으로 확장할 계획이다. 이 문서는 [System Context](./c4-context.md)를 기준으로, 확장 계획을 감안해 도메인 경계와 이름을 정리한다.

## 1차 구현 범위 도메인

| 도메인 | 책임 | 비고 |
|---|---|---|
| `User` | 고객(구매자) 프로필/회원 정보 소유 | 인증(Auth)과 분리 |
| `Auth` | 로그인/토큰 발급, 권한(role) 관리 | `User`·`Provider` 양쪽 역할을 하나의 도메인에서 role로 구분해 처리. 별도 인증 시스템으로 분리하지 않음 |
| `Provider` | 판매자(현재는 공연 주최자)의 상품 등록·관리 | 구 명칭 `Organizer`/`Admin`. 향후 숙소 호스트·항공사 등도 이 도메인으로 편입 가능하도록 범용 이름 채택 |
| `Product` | 판매 대상(현재는 공연) 정보 | 공통 속성(제목, 가격, 판매기간)과 콘서트 전용 속성(회차, 아티스트 등)을 개념적으로만 구분. 실제 멀티버티컬 스키마 분리는 피벗 시점에 진행 (YAGNI) |
| `Inventory` | 판매 가능 수량/상태 관리 (현재는 좌석) | 구 명칭 `Seat`. 동시성 제어(락, TTL)와 데이터 정합성이 핵심 관심사라 `Product`와 분리. "좌석"이 아닌 "재고"로 일반화해 향후 숙소 객실·항공 좌석까지 재사용 가능 |
| `Booking` | 예약/예매 트랜잭션 처리 | `User`·`Product`·`Inventory`·`Payment`를 조합하는 트랜잭션 경계 |
| `Payment` | 고객 결제·환불, PG 연동 | 정산(`Settlement`)은 별도 도메인으로 분리 예정이므로 여기 포함하지 않음 |

## 보류 (1차 구현 이후 추가 예정)

| 도메인 | 보류 사유 |
|---|---|
| `Queue` (대기열) | 대용량 트래픽 대응은 1차 구현 이후 진행 예정 (Redis Pub/Sub → Kafka Stream 전환과 함께 다룰 예정) |
| `Notification` | 1차 범위는 결제·예매 기능에 집중, 알림(이메일/SMS/푸시)은 이후 추가 |
| `Settlement` | 정산은 배치성이며 정합성 요구가 결제와 다름. `Payment`에서 분리해 별도 도메인으로 나중에 설계 |

## 주요 결정 배경

- **`Provider`/`Product`/`Inventory` 네이밍을 범용화한 이유**: 콘서트 티켓팅 전용 용어(`Organizer`, `Seat`)를 쓰면 숙소/항공으로 확장할 때 도메인 자체를 새로 만들어야 한다. 이름을 미리 일반화해두면 피벗 시점에 내부 구현만 바뀌고 도메인 경계는 유지된다.
- **`Auth`를 `User`와 분리한 이유**: 로그인 방식(자체/소셜) 변경이나 `Provider` 인증 추가 시 회원 프로필 도메인이 흔들리지 않도록.
- **`Inventory`를 `Product`와 분리한 이유**: README에 명시된 이 프로젝트의 핵심 문제(대용량 트래픽, 데이터 정합성)가 대부분 재고/좌석 동시성 이슈에서 발생하므로, 변경 빈도와 일관성 요구가 다른 두 개념을 처음부터 분리.
